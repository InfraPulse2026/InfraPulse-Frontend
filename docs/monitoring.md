# Мониторинг и Linux Audit — v0.7.0

## Сетевые интерфейсы

Карточка Asset → Метрики → Сетевые интерфейсы Collector. Источник берётся из конкретного native binding, запрос истории содержит agent_id и device_id. Последние 100 samples и до 500 интерфейсов в sample — ограниченная выборка, а не вся история сети.

Показываются административное/операционное состояние, точные RX/TX bytes, errors/dropped, готовые скорости в B/s и график выбранного interface ID. Клик по интерфейсу открывает восемь счётчиков/скоростей, разрядность, адреса, MAC, MTU, link speed и время выбранного наблюдения. При чтении детали фиксируется snapshot значений; новые samples не подменяют открытую карточку.

Семантика взята из неизменённого Collector 215d33a:

- uint64 остаётся десятичной строкой, максимум 18446744073709551615; небезопасный Number не «восстанавливается» округлённым;
- отсутствующая CounterMetadata сохраняет legacy 64-bit семантику; присутствующая маска доступности имеет приоритет;
- пропущенный protobuf scalar означает ноль только внутри присутствующего и квалифицированного сообщения/показателя; отсутствие всего сообщения counters/rates означает неизвестное;
- CounterWidths=0 — неизвестная/агрегированная разрядность, не гарантия 64 bit;
- доступны только Agent-provided rates; браузер не вычисляет delta, wrap/reset или скорость из накопительного счётчика;
- неподтверждённые/отсутствующие rates становятся null-разрывами графика, а не искусственными нулями;
- совпавшие или отсутствующие interface IDs не объединяются по имени/IP; неоднозначные строки исключаются с предупреждением;
- новое наблюдение не доказывает эффективное online-состояние устройства.

## Внешние метрики и Prometheus

Таблица ExternalMetrics поддерживает limit/offset по 50. Endpoint не возвращает total/has_more: следующая страница доступна при полной текущей, пустая завершающая страница допустима. Большие целые не теряют точность в таблице.

Prometheus history использует только source_instance_id/target_id/mapping_id из bindings и сохранённых mappings. Произвольный PromQL/URL не вводится. Можно выбрать временное окно и явно обновить его конец до текущего времени; шаг ограничивает отображаемый объём примерно 500 точками. Range API не имеет cursor-пагинации: интерфейс не придумывает её. Качество complete/partial/no_data отображается из ответа, evaluation time не выдаётся за момент физического измерения. Небезопасные числа пропускаются на графике.

## Аппаратные наблюдения

Из строки hardware открывается предметный контекст: observation key, resource/subject/binding, источник, scope, health/rollup/power/operational state, freshness, три времени, качество часов/данных и relation IDs. Сырые дополнительные поля остаются раскрываемыми.

Health, power и freshness не подменяют друг друга. Power Off не превращается в Critical. Подключённый Agent не делает автоматически свежим каждый датчик.

История идёт по observation_key через backend next_after_id. Есть следующая/предыдущая страница; график относится только к текущей странице до 200 samples. Разные observation keys и единицы не объединяются в одну линию. При смене Asset/выбранного наблюдения курсор сбрасывается. Некорректный/повторяющийся cursor не запускает бесконечную загрузку.

## Поиск логов и Linux Audit

Открыть Логи и аудит → Дополнительные фильтры. Параметры одинаково применяются к потоку и audit-группам:

- точные Agent/Device/Source/Host/Process;
- audit record type, event ID, executable;
- severity/facility, UID/AUID/PID и success=true/false/unknown;
- from/to с явным часовым поясом в запросе;
- PostgreSQL word/phrase q либо буквальная contains, одновременно не отправляются.

Время в форме — местное время браузера, в API отправляется UTC RFC3339. Подстрока требует обоих концов и окна не длиннее семи дней. Проверяются UTF-8 лимит 256 байт, uint32 для числовых фильтров, календарные даты, порядок периода, безопасный cursor. UID=0, PID=0 и success=false не исчезают как «пустые».

Группа Audit показывает event ID, источники, типы, количество выбранных строк и outcome. Детали открываются только по ключу audit-группы, возвращённому backend, и сохраняют текущие фильтры. У отдельных записей видны UID/AUID/PID, executable, результат и проектированное сообщение. before_id приходит из backend и не вычисляется из timestamp. Полнота события остаётся unknown: даже 53 строки не доказывают, что транспорт собрал всё. Это Linux Audit, а не аудит административных команд.

## Проверки

Новые browser-сценарии: network precision/zero/unknown + external pages; hardware cursor; Audit UID=0/false + paged records; contains window rejection; mapping-bound Prometheus range и обновление окна. Все данные в них явно simulated. Новые unit/contract проверки покрывают protobuf masks, uint64 bounds, invalid rates, ownership IDs, RFC3339/calendar/timezone, UTF-8, zero filters, cursor и валидность typed fixtures.

Новый живой стенд не запускался. Проверка на настоящих Collector/Zabbix/Prometheus/оборудовании, нагрузка и развёртывание переданы другим разработчикам: team-handoff.md.
