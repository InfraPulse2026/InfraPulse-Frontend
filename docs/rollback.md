# Откат типизированных команд Agent — v0.6.0

## Область

Раздел «Команды и откат» использует существующие `/api/commands`, `/api/commands/{id}`, `/events`, `/snapshot`, `/rollback`, `/api/commands/policy` и `/api/snapshots`. Это восстановление снимка ресурса Agent после типизированного действия. Конфигурационные снимки Ansible и baseline остаются отдельными сущностями: endpoint их отката в текущем OpenAPI отсутствует. UI его не придумывает.

Frontend не меняет Agent, backend, protobuf, политику разрешений или защищённые ресурсы. Самостоятельное создание enable/disable команд в этом срезе не добавлено: журнал показывает существующие команды, для подходящей исходной команды доступен rollback.

## Просмотр

1. Открыть «Команды и откат». Все роли с data.read видят журнал и политику.
2. Можно отобрать по точному Agent ID, Device ID и состоянию. ID не заменяются именем/IP и не объединяются между агентами.
3. Вкладка снимков показывает ссылки, владельца ресурса, статус и время регистрации. Содержимое снимка не скачивается из Agent.
4. Карточка команды показывает исходное условие, серверное состояние, Agent result, отдельную verification, origin/rollback links и до 1000 событий.

Запросы списков используют limit=50 и offset. Активные команды перечитываются каждые 3 секунды; queued/dispatching/sent/accepted/running не означают успех. Для терминальных исходов есть ручное обновление. Состояние uncertain остаётся неопределённым и не вызывает повторного исполнения.

## Условия отката

Кнопка доступна роли с commands.write при выполнении условий:

- политика backend: enabled, allow_rollback и allow_disable;
- исходная команда success, результат и verification однозначны;
- снимок candidate, ещё не занят другим откатом;
- совпадают Agent, Device, interface, origin command и snapshot ID результата;
- зафиксировано after_admin_up, проверка относится к этому интерфейсу и согласована с наблюдением;
- ресурс не находится в явно опубликованном защищённом списке;
- оператор явно выбрал ожидаемое состояние перед откатом, совпадающее с after_admin_up, и timeout 1–60 секунд.

Это предварительные проверки UI. Backend дополнительно проверяет сессию/права, возраст inventory/telemetry, доступность устройства, capability resource.rollback, защищённые алиасы и management interface. Окончательное разрешение остаётся за backend/Agent. Повторный откат отката эта форма не предлагает.

`false` — административно выключен, не «значение отсутствует». Ожидаемое состояние **перед** откатом не является желаемым состоянием **после** него. Что восстановится из снимка, определяет Agent; первоначальное наблюдение backend показывается отдельно как справочная информация и не выдаётся за содержимое снимка.

`expires_at=null` означает, что срок хранения не передан Agent. Это не бессрочное хранение и не гарантия доступности; агент может отклонить уже отсутствующий снимок.

## Подтверждение и конфликт

В подтверждении фиксируются origin command, Agent/Device/interface, snapshot ID, ожидаемое состояние и timeout. Перед POST UI перечитывает команду, снимок и политику. Если контекст изменился, POST не выполняется. Новые значения не подставляются в открытое подтверждение.

POST `/api/commands/{origin}/rollback` отправляет только существующий RollbackRequest: `{expected_admin_up,timeout_seconds,confirmed:true}`, CSRF и Idempotency-Key. Snapshot ID в body не добавляется: его выбирает backend по origin. API не предоставляет отдельного expected_snapshot_id/CAS revision, поэтому клиентская повторная проверка не является атомарной серверной блокировкой. Backend выполняет собственную транзакционную проверку и возвращает привязанный rollback_snapshot_id. Для новой команды показывается именно сохранённая сервером ссылка.

После 200/202 появляется ссылка на отдельную команду отката. Это принятие запроса; конечное состояние и verification нужно смотреть в её карточке. При 409 или сетевой ошибке старое подтверждение блокируется. Автоматического повтора нет. Если ответ потерян, нужно перечитать origin snapshot и journal: rollback_command_id может уже указывать на сохранённую команду.

Ключ сохраняется для неизменного origin/snapshot/payload в пределах открытой карточки. Форма не подменяет действие новой ревизией после конфликта и не снимает защищённость интерфейса.

## Закрытые снимки Ansible

Их просмотр остался отдельным административным действием с аудитом. В карточке job скрытие просмотра освобождает query cache; focus/refetch не перечитывает закрытую конфигурацию автоматически. При переходе к другому job требуется новое явное открытие снимка.

## Проверки и передача

Guard-тесты проверяют false/null, policy, ownership, lifecycle, verification, неизвестный срок и блокировку конфликтов. Browser-тесты работают с явно simulated fake Agent: read-back, uncertain result, Viewer, отсутствие POST при изменённом контексте и блокировка повторного подтверждения.

Живой rollback RouterOS/Collector, mTLS/CA и реальное отключение интерфейса **не выполнялись**. По решению команды это отдельная приёмка других разработчиков; аналогично развёртывание и публикация. Полный список — `docs/team-handoff.md`.
